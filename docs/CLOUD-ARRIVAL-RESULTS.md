# 雲端旋轉時間量測（2026-10-27，Asia/Taipei）

## 方法

在同一雲端機器依序跑兩輪完整追蹤回歸，每輪飛機與軍機各量測 10 次。第一輪只增加重複次數與統計；第二輪使用抽出的同一個瀏覽器 fixture，額外被動記錄 preRender/postRender。兩輪均不平行執行建置或重型測試，不使用離線圖磚，不修改 500 ms 或角度斷言。這是同機重複量測，不是跨機抽樣。

Node v24.19.0；Chrome/154.0.8037.57；1280 × 800，devicePixelRatio 1；renderer：`ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)`。容器 CPU quota 為 4 cores。

下列逾時值是「失敗被觀測到的時間」，不是已完成旋轉的實際時間；例如 500.1 ms 代表計時器在門檻附近回報未完成，真實完成延遲仍未知。這些值皆保留在統計中，沒有排除失敗或把它們當成成功。P95 採最近秩法；10 筆資料的 P95 等於最大值。

## 原因判斷與最小變更

- 診斷輪飛機的 10 次觀測都在第一個 preRender 前到期：時間門檻內沒有可供觀測的完整場景更新，不能把它描述為「已執行旋轉但角度錯誤」。
- 軍機的首個 preRender 在約 296.6–345.3 ms，首個 postRender 約 298.5–354.0 ms，觀測到的旋轉誤差均接近 0°。多數樣本未能在剩餘時間內再取得可見的 reveal frame；唯一記錄到的較晚可見 frame 在約 903.7 ms，角度仍接近 0°。隱藏中的約 86° 是 fixture 刻意植入的值，不是可見錯誤被忽略。
- 此環境使用 SwiftShader 軟體渲染。兩輪皆 20/20 失敗，顯示它在目前工作負載下無法穩定滿足呈現時間預算，不能只歸因於偶發雲端波動。
- 現有測試方法把旋轉邏輯、場景更新與取得兩個渲染 frame 的延遲合併為一個門檻，因此對渲染吞吐量敏感。觀測支援「雲端軟體渲染／frame 排程瓶頸」為主要方向，但沒有硬體 GPU 對照，無法排除其他場景工作或建立跨機因果結論。
- 沒有證據支持修改飛機旋轉公式或降低精度。本 PR 的最小變更是可重複取樣、保留失敗的統計與被動 frame 診斷，並共用原 fixture；應用程式、500 ms 門檻和原判定皆不變。沒有把較早的 preRender 取代原 postRender 判定來製造通過。
- 下一個效能工作應在可用硬體 GPU 的相同視窗與資料下做對照，再以效能 trace 找出最慢的場景／GPU 工作。若需拆分邏輯與呈現效能測試，必須保留獨立的 500 ms 效能 gate，而不能刪除這些失敗。

## 驗證與限制

- 基準完整回歸：107 passed / 20 failed / 0 skipped，exit 1；20 項失敗均為重複的原旋轉檢查。
- 診斷完整回歸同為 107 passed / 20 failed / 0 skipped，exit 1；沒有非旋轉項目的新增失敗。整理後的真實地圖工具也通過 Esri、OSM、非平坦地形、三組字型與地形高度 API 檢查。其他驗證於本次 PR 描述列出。
- 原始 JSON、逐筆網路紀錄與截圖保留在 ignored `qa-artifacts/`；本文件只提交無機密的數值摘要，不提交 API 金鑰、憑證、瀏覽器資料庫或環境設定值。
- 第一輪包裝器的被動網路紀錄未涵蓋非同步執行期，檔案為空；該輪原 runner 的 127 個測試確實完成，但不把空檔案當成網路驗證。已將 runner 頂層入口改為 await，第二輪確認觀測器持續記錄至 gate 完成。
